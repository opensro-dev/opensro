# Optional 110-cap expansion

Port-only, not native. The default stays v1.150 with cap 90, and every switch below is off by default. The expansion
adds later-client content on top of the native tables, joined by codename. Native rows, IDs and names never change.

## Switches

The switches do not imply one another. A build switch changes the published data, so the build and the server must
agree.

| Switch | Where | Effect |
| --- | --- | --- |
| `SRO_ALEXANDRIA` | Build and server | The Alexandria city variant, which the other imports build on |
| `SRO_LEVEL_CAP=110` | Server | Raises the stopping level. Unset, `off`, `false`, `0` or `90` keeps 90; other values fail startup |
| `SRO_CAP110_ITEMS` | Build | Equipment for degrees 10 and 11, the Blue Berserk chains' 18 quest items, and the Energy of Life scrolls with their shop rows and texts (the last two need `SRO_LEVEL_CAP=110` at build) |
| `SRO_MALL_AVATARS` | Build | The later client's mall avatars: 146 outfits, hats and attachments, among them the Ottoman ("Turkey") set. **On by default** (cosmetic, owner-approved); `off` removes them. Skipped when the later client is absent. Rows with absent files (Santa, 2011 Saint Warrior and Dark Knight, Chingchu 2) are left out; the Nasrun wearables have no worn model by design and come from `SRO_NASRUN` ([NASRUN.md](NASRUN.md)). The 98 the later Item Mall sold are listed in the Item Mall at the native tier (dress 130, hat 30, attachment 15 silk); the other 48 are GM grant only. No drop or event |
| `SRO_HONOR_GOODS` | Build | The rest of the Training Camp honor line in every honor store: degree 10 and 11 honor weapons, Chinese honor shields, the European honor weapons on a third tab, and the degree 10 and 11 repair stones. Needs `SRO_CAP110_ITEMS` for the degree 10 and 11 rares |
| `SRO_CAP110_SKILLS` | Build | Skill ranks up to mastery 100 from the later client |
| `SRO_CAP110_SKILL_DATABASE` | Build | Path of a skill export that adds mastery 101-110 |
| `SRO_CAP110_MONSTERS` | Build and server | Field monsters, nests, monster skills, loot tables and rewards |
| `SRO_CAP110_MONSTER_DATABASE` | Build | Directory of the monster export; optional — unnamed, the field builds from the VSRO client alone |
| `SRO_CAP110_LEVEL100` | Server | Admits the level 100 monster slice separately from levels 101-110 |
| `SRO_CAP110_SET_BONUSES` | Server | Applies degree 10 and 11 set bonuses |
| `SRO_CAP110_QINSHI` | Build and server | Qin-Shi tomb upper floors, `cap110-qinshi.txt`. Needs `SRO_CAP110_MONSTERS` |
| `SRO_CAP110_TEMPLE` | Build and server | Temple family, `cap110-temple.txt`, in its instanced worlds. Needs `SRO_CAP110_MONSTERS`; the importer and the server loader both refuse it otherwise |
| `SRO_PHARAOH_TOMB` | Build and server | Pharaoh Tomb 1-3. Needs `SRO_CAP110_MONSTERS` |
| `SRO_CAP110_QUESTS` | Build | The Blue Berserk quest chains and what exists only for them: the 52 quest rows and their texts, the eleven quest monsters and their skills, and the two trial arenas (the quest logic follows). Needs `SRO_LEVEL_CAP=110`; the quest items are not behind it (see `SRO_CAP110_ITEMS`) |
| `SRO_HWAN_NIYA_CAPTURE_RATES` | Server | The Niya trap quest's roll as three whole percentages `nothing,flutter,normal` that sum to 100. Unset keeps the original (2 and 28 of 101 for a Normal and a Flutter Spirit) |
| `SRO_HWAN_SUN_RELIC` | Server | The Sun God relic dig's chance as a whole percentage 0-100. Unset keeps the original (11 of 101). A fraction, a sign, a unit or a value outside 0-100 refuses startup |
| `SRO_HWAN_3_FAST_DROP` | Server | `on`: the Alexandria ostracon steps (`QNO_SD_HW_002` to `_008`, and `_010` to `_016`) drop ten quest items per kill, never more than the quest still needs. Off (default): one |
| `SRO_PHARAOH_TOMB_GEAR_RATE` | Server | Multiplies tomb elite and unique equipment rolls, 2 to 20. Unset or 1 is unchanged |
| `SRO_SKYTEMPLE` | Build and server | Sky Temple fields A-D from the v1.696 client, `skytemple-monsters.txt`. Runs inside the Alexandria variant build; off leaves every imported row out |
| `SRO_ARABIA` | Build and server | Arabia continent from the v1.696 client and the ISRO-R nest extraction, `arabia-monsters.txt`. Runs inside the Alexandria variant build; off leaves every imported row out |
| `SRO_ARABIA_NESTS` | Build | The authored nest extraction the Arabia importer reads (`arabia-population.json`). No default: maintainers' data, not in a public clone; with `SRO_ARABIA` on and this unset the variant build stops and names it |

For learnable high ranks, `SRO_CAP110_SKILLS`, `SRO_CAP110_SKILL_DATABASE` and `SRO_LEVEL_CAP=110` must all be set.
With the database tier published and the cap at 90, the ranks show on the board but cannot be learned, and the
gameworld warns once at startup.

Rebuild the level catalogue with the same cap as the deployment. Lowering the cap stops further level gains; it does
not lower characters, remove items or undo rewards. A rollback of a live shard needs its own content and state policy.

## Building

`scripts/build_alexandria_variant.py` runs the importers in order and writes into the optional variant root. The native
extraction is never the output. Turning a flag off removes the shard that flag owns and restores the native manifest.
Edited or unmarked shards are refused, not overwritten.

A rerun with the same code, `SRO_*` flags and source files, over a tree untouched since its last build, is skipped in
seconds (`variant_stamp.py`); `--force` rebuilds anyway. After a build, `variant_settle.py` gives every file whose
bytes did not change its old mtime back, so the asset build downstream reconverts only what changed.

Published IDs stay with their codes through the checked-in pin `scripts/data/published-identities.json` (#3815): the
character, item and skill ids the last release's catalogue lists. A full variant build removes the importers' markers
(such as `extracted/.opensro-cap110-monsters.json`) and numbers afresh, so without the pin a flag that adds early rows
(`SRO_ROC`'s set armour) moved every later import's ids. Every allocator follows `scripts/published_ids.py`: a released
id stays with its code, a released id whose code this build does not stage stays reserved, and a new code numbers above
them. Refresh the pin from each published release before the next one is built:
`py -3 scripts/pin_published_identities.py <catalogue folder> --textdata <server textdata>`. The textdata pins every
object the release served, not only the catalogue's monsters: a stored pet or an appointed gate is named by id (#4019).
A refresh keeps codes the catalogue drops and refuses a moved id. Losing the database input on a later build fails, so learned skills cannot silently disappear.

Compare the two clients, without extracting anything:

```text
python -B scripts/analysis/compare_cap110.py --native-root <native-client> --vsro-root <later-client>
python -B scripts/analysis/skill110_scope.py --native-root <native-client> --vsro-root <later-client>
```

The results go to `.state/cap110-comparison.json` and `.state/skill110-scope.json`.

After every import and server export, run `scripts/analysis/check_identity_parity.py`. It joins the client's and
server's character, skill and item tables by codename, and fails on a differing ID or a one-sided codename.

`cap110_monsters.py` refuses an export that does not match its pinned backup hash (`require_pinned_export`). The import
marker keeps the hash of each exported file.

The export is optional. With none named, the field family builds from the VSRO client alone: `cap110_monsters.py`
joins the MOB_SD_ rows of characterdata to their npcpos placements and writes one nest per outdoor placement with a
synthesized ordinary posture (one monster on its point, a 1-3 second respawn, sight 100 — the commonest authored
values of the shipped population evidence, recorded as an inference in the tool). Stage 1 seeds the field terrain
from the same placements. The tomb and qinshi families still require the export, and rewards carry no
database rules (below). The temple bands are not a family here: `god_import.py` builds them from the ISRO-R
export and the v1.696 client ([GOD.md](GOD.md)).

Field gear without the export (#3405): the committed vSRO backup's enabled degree-10/11 equipment assignments (66
ordinary and 66 Seal D10, 22 ordinary D11 A, with their own weights) join the items `SRO_CAP110_ITEMS` installed. With
that flag off nothing joins, and levels 101-110 fall back to degree-9 gear. No source authors an ordinary equipment
class above level 101, so 102-110 mirror D10's banding one degree up (an inference, owner's choice 11-13): group 30
at 102-104, 31 at 105-108, 32 at 106-110, each at 0.0035. The backup's Seal rows above 94 never roll, so Alexandria
drops no Seal of any degree. The build refuses a normal row 101-110 with no class.

Named again, the export's authored nests, tactics and drop assignments replace the
synthesized posture wholesale.

## Equipment

`scripts/cap110_item_import.py` adds 824 items: 112 weapons, 16 shields, 648 armor pieces and 48 accessories, in
ordinary and Seal grades at degrees 10 and 11. Weapons keep the first ID range. Requirements, statistics, sex and race
stay as authored. Linked codenames must resolve inside native plus imported rows.

- With `SRO_ROC` on as well, the 72 Roc set pieces (`ITEM_ROC_*_SET`, class 30) join too ([ROC.md](ROC.md), step
  5c). Their identities stay reserved when a later build leaves them out.
- Set gear, 376 rows, imports beside its group catalogue. Set bonuses apply only with `SRO_CAP110_SET_BONUSES` on.
- The v1.150 client has no set rows, so an armor tooltip shows no set bonus by itself. With `SRO_CAP110_SET_BONUSES` on,
  the world-entry blob lists each set's tiers (`equipmentSets`), and the Experimental window's "Set bonus on item
  tooltips" row (Interface tab, Items and mall, off by default) adds a block to an armor tooltip: the set name, worn pieces out of the
  total, and each tier with the one in force highlighted. The wording is the port's own; the armor and accessory set names
  (Destruction, Immortality, Myth, Legend; `SET_NAMES` in `item-tooltip-set.ts`) translate the Korean group names in `refsetitemgroup`, and 1.188's data holds no text for them.
- Sealed set pieces (`_SET_A_RARE`, `_SET_B_RARE`, rarity 6) and "Seal of Nova" (the first seal tier of degree 11) are
  the later client's. They apply only with `SRO_CAP110_ITEMS` built and `SRO_LEVEL_CAP=110` on the server: on such a
  shard a rarity 6 piece takes the sealed loot rules (always rolls its options, no extra nonrepair option), the extra
  variance roll, the server's seal announcements, and the seal tooltip, shine and quick-sell refusal in the client (the
  client reads the shard's published level cap). The chat readers that colour a drop announcement or mark a sun drop
  (`sealNoticeColorArgb`, `isSunDropChatLine`) do not read the cap, so a rarity 6 announcement keeps the plain colour and
  has no sun marker; that is deliberate and pinned by a test. The sun event (`progression/sunevent.go`) keeps the native rarity 2 test too, so on
  an expansion shard a rarity 6 sealed set piece is ordinary prey where a rarity 2 sealed piece is excluded; the event is
  native and this port-only rule does not extend it. At cap 90 the piece is plain everywhere and degree 11 `_RARE` reads Seal of Star. Degrees 1 to
  10 and rarity 2 are native and unchanged.
- Links to degree 12 items are trimmed and recorded, because the degree 12 conversion is out of scope.
- Missing descriptions stay absent. Every name is required.
- Circlets and accessories without a worn mesh keep their icon and drop model.
- New particle effects live only in the variant overlay. Later sound modifiers and unsupported particle selectors fail
  the import.

`scripts/alexandria_shop_d10.py` stocks Alexandria's own shops. `STORE_SD_SMITH` and `STORE_SD_ARMOR` are copied from
Khotan's stores, which stay unchanged, and `STORE_SD_ACCESSORY` is restocked in place. By default each store then
stocks what official Alexandria sold (#2846; the source is iSRO-R, the official city that has a smith): degree 11
grade A goods only at the smith and the accessory, degree 11 set armour only at the armourer, and of the degree 11
alchemy only the speed potion. The port's own degree stock - each degree 9 ordinary good gaining the degree 10 good
of its family, and each degree 10 good its degree 11 twin beside it - ships only with the build flag
`SRO_ALEXANDRIA_PORT_STOCK` on; unset or off, the build stocks the official goods. A tab never exceeds the 45 slots
of the largest native tab; the lowest degrees drop first. Prices come from the item's price column, an inference
because v1.150 has no degree 10 shop. Grades B and C, and rare or Seal items, are not stocked.

Honor stores (#3548). The warehouse keepers' Training Camp stores sell goods for gold plus honor points. Native,
always on: every honor store is laid out as iSRO-R's live tables lay it - the weapon tab holds, per kind, the degree 8
then the degree 9 honor weapons (grades A-C), and the stone tab the degree 8 then 9 repair stone. v1.150 authors the
degree 9 packages and prices but stocks only degree 8. Port-only, behind the build flag `SRO_HONOR_GOODS`: the rest of
the line the client's resinfo authors. The weapon tab's first page stays native; its second page carries degrees 10
and 11, then the Chinese shields, a third tab sells the European honor weapons, and the stone tab gains the degree 10
and 11 stones. Every derived item follows the rule all 84 shipped honor rows follow: the `_RARE` row, no trade, borrow
or drop, required level -2/+2/+6 for grades A/B/C, and a flat price per degree and grade with 40% back on sale. Degree
11 has grade A only, since no source authors a B or C rare at that degree. Prices for degrees 10 and 11 continue the
native step from degree 8 to 9 linearly (an inference: no source prices them). Unset or off, the build is the native
layout byte for byte.

GM spawn: `/MAKEITEM ITEM_CH_SHIELD_10_A 1`. Rare variants append `_RARE`.

## Skills

`scripts/cap110_skills.py` and `scripts/cap110_skill_import.py` add 757 ranks through mastery 100, 555 trainable and 202
chain rows. `scripts/cap110_skill_database.py` adds 761 more for mastery 101-110 from an explicit `_RefSkill` export.
That makes 1,518 rows, with IDs from 31925 to 33442 and no new mastery.

- Groups, chains and prerequisites are remapped by codename. A later group that no shared rank uses gets a fresh ID
  above the native range.
- `scripts/cap110_skill_effects.py` merges the later animation sets native lacks. Native rows win. A later row that
  names an unknown native animation state is refused.
- A mastery is bounded by `MasteryLevelCap` (120) and the character's level.
- The v1.150 client's board never builds a cell for a skill above mastery 90. The browser client does not port that
  gate, so new ranks appear as the mastery reaches them (`skill-slot.ts`).
- About 46 animation bases have no set in either client. They are passive families that are silent in the original too.
- A press audit must not treat passives or the instant imbue path as missing casts. Of the 536 new root candidates, 62
  are passives and 20 use the instant path.

The skill tables differ between clients in numeric IDs, groups and chains, so a converter must remap by stable identity
and never copy the later numbers. The port's skill compiler decodes all imported rows, but decoding is not proof that a
skill behaves correctly in play.

## Alexandria world

- **Field monsters:** 29 types, 1,519 nests and 78 added skills (the export build; a client-only build places the
  species npcpos carries, one nest per placement). The importer reserves every published identity before
  allocating new ones.
- **Terrain:** field regions seed the same connectivity walk as the city, bounded by the source availability bitmap,
  so connecting ground and mountains come along.
- **Dimensional gates:** Abundance Ground to Storm and Cloud Desert, and Forbidden Plain to Kings Valley. Both are free,
  need level 95 from Delta, and return free without a level condition. With the monster flag on, gate projection uses
  the 110 ceiling; off, it keeps the level 90 ceiling.
- **Map:** overview textures covering imported regions use the later bytes. City markers and labels project into the
  native table through `scripts/alexandria_map_tables.py`. A new label is admitted only if its text key resolves.
- **Unique presentation:** the imported Apis keeps grade 8. The client grade table has a port-only grade 8 entry for the
  Unique title and icon. No native monster reaches it.

## Pharaoh Tomb

Kings Valley has one gate, `GATE_TOMB_GATE_IN`, linked both ways and free to three exits,
`GATE_TOMB_GATE_OUT_1..3`. The tombs are ordinary outdoor regions, so they reuse the field pipeline: 30 nests each, 17
monster types each, levels 100-110, and five boss families.

These decisions are inferences, not native evidence:

- Each tomb is its own permanent world, registered port-only as `INS_PHARAOH_TOMB_1..3` with IDs 57-59. A variant built
  with the tomb gates only boots with `SRO_PHARAOH_TOMB` on. Off, the catalogue is refused at `names unknown world 57`
  rather than flattening three tombs into the field.
- Bosses are single-spawn nests with their authored respawn delay. The source has no trigger data, so instance
  triggers are not ported.
- The unplaced `GATE_TOMBOSIRIS_*` rows are not carried.

The server side is `monster/pharaoh_tomb.go`, sharing nest validation with `cap110.go`.

## Sky Temple

`scripts/skytemple_import.py` imports the four Sky Temple fields (`RN_OTHER_SKYTEMPLE_A` to `.._D`, 288 sectors at
x 217-233, y 82-100) from the v1.696 client into the Alexandria variant build under `SRO_SKYTEMPLE`. The later client
is read from `SRO_V1696_ROOT`, defaulting to `inputs/sro_1696` next to the checkout, and its archives are checked
against `scripts/v1696_archive_pins.json` when that file exists. The import runs inside
`scripts/build_alexandria_variant.py`, so it needs that build; the flag does nothing in the plain native build.

These decisions are inferences, not native evidence:

- The monsters keep their authored levels 131-178 (the v1.696 design tops out past 140). Nothing here raises the
  player level cap: `SRO_LEVEL_CAP` still only admits 90 or 110, and level-ups past the cap remain closed. Kinds
  past the placed range (the two level-178 uniques are summon-only in the source) stay out.
- Placements come from the source client's `npcpos` wherever it names the monster: 428 nests for 67 kinds, each a
  client-only nest in the posture of the imported Alexandria fields, as recorded for this import (#3269). Eight kinds the source never places
  (summons and one clone) are left out rather than authored.
- The entry gate stands in Jangan (`RN_CH_JANGAN`, re-homed from the source's Jupiter-town gate, which has no region
  here). Fields A and B keep their source links; field C's source links name buildings that do not exist, so its
  entry and return are authored onto the entry gate, and field D, which has no gate at all, gets an authored gate
  pair (teleportdata 352, building `STORE_OTHER_SKYTEMPLE_D_TO_TOWN`) landing on its fullest region. Every imported
  or authored arrival names world 1, because the later-client world numbers 132-134 do not exist in the server's
  portal catalogue. Link level conditions are clamped onto `SRO_LEVEL_CAP` like every other imported gate.
- Twelve sound paths and one effect (`monster/system_appear.efp`) are absent from the input clients. Absent sounds
  and effects are recorded in the import marker and skipped rather than failing the build, matching what the native
  models do about that same effect. Everything else the closure names is required.
- World-map overview art for the four fields is not imported; the fields are reachable only by gate.

The server side is `monster/skytemple.go`, admitting `MOB_SKYTEMPLE_` kinds at authored level 131-178 behind
`SRO_SKYTEMPLE`. The drops are the native posture (no new reward table), and the importer adds no spawns for kinds
the source never placed.

## Arabia

`scripts/arabia_import.py` imports the Arabia continent (Baghdad town, the three fields, Petra, the Baghdad dungeon
and the garden; 264 `RN_ARABIA_*` regions) into the Alexandria variant build under `SRO_ARABIA`. The terrain,
navmesh, character rows and models come from the v1.696 client (read from `SRO_V1696_ROOT`, defaulting to
`inputs/sro_1696` beside the game root); the authored nests come from the ISRO-R nest extraction
(`SRO_ARABIA_NESTS`, `arabia-population.json`, no default, like the other later worlds' population exports), whose
sha256 the marker records on every run. Neither source is committed.

These decisions are inferences, not native evidence:

- The monsters keep their authored levels 120-130. Nothing here raises the player level cap, as with the Sky
  Temple kinds past it. The 51 placed kinds ride `characterdata_200000.txt` / `skilldata_200000.txt` (the bands
  below are taken: 120000 cap-110, 130000-150000 the pet import, 310000 the Blue Berserk quest monsters (280000-300000 are the Colosseum and the Bandit and Hotan fortresses), 160000 the Sky Temple, 170000 Jupiter,
  180000 the second hunting grounds, 190000 the GOD temples).
- The client carries 264 regions; the backup binds only 173. Terrain and navmesh import for 263 of them (the
  boss lair's sector exists in neither client; only its region row imports), and nests land only where the
  authored population names them, so Petra and the garden stand populated by nothing but their authored NPCs
  until a later slice sources more.
- The dungeon's 237 nests name world 112 (`GROUP_ARABIA_DUNGEON`), registered port-only while the flag is on
  (`world/arabia`, `instance.ArabiaDefinitions`); their spawn kind 1 rides the rows, as the temple family's does.
  Worlds 113-115 (boss lair, Petra, garden) carry no nests and no gates in either source and stay unregistered,
  so the boss lair and the garden are imported on the map but not yet reachable.
- Two uniques' spawn points share an overwrite cap of 1 in the source (MOB_ARABIA_KARKADANN, MOB_ARABIA_MUSTAFA,
  11 points each). They project onto the loader's hive key under the kind's codename with the authored cap, so
  one of each is alive at a time across its points; the nest ids are listed in the marker.
- Baghdad's NPCs stand and talk (character rows, npcpos standings, npcchat rows, name texts), but their shops do
  not ride: a store sells only when it is a native one (the Alexandria rule), and Baghdad's stores sell gear the
  v1.150 item tables do not have.
- Travel: the dungeon chain stands as authored, with its town portal building (absent from the source) authored
  beside its Baghdad arrival. No source gate leads into Baghdad from the shipped world, so the entry is authored
  at Jangan beside `STORE_CH_GATE`, in the Sky Temple entry's shape; see `scripts/arabia_gates.py`.
- 132 nests of one thief kind carry an inverted authored respawn pair (min 7, max 1) in the backup. The native
  delay draw widens only upward, so the pair already means a fixed 7-second draw; the importer stores (7, 7) -
  the same draw, inside the loader's min <= max invariant - and lists the nest ids in the marker.
- What the sources do not hold is recorded, never invented: two nameless event props the client plants (their
  name keys exist in no text table of either client) are skipped and logged; one material the archives name but
  no client holds, four later-format files the shared readers cannot parse, five sounds and one effect are
  listed in the marker; 76 talk keys (the `SN_..._PS` family) resolve in no text table of either client - the
  native tables leave the same column dangling - and are recorded likewise.

The server side is `monster/arabia.go`, admitting `MOB_AR_`/`MOB_ARABIA_` kinds at authored level 120-130 behind
`SRO_ARABIA`, the town and fields in the default world and the dungeon in world 112. The drops are the native
posture (no new reward table). The quest mechanics are `quest/arabia_quests.go`: 29 of the 82 quests (9 talks,
20 hunts) whose later-client evidence is complete - targets, counts, NPCs, rewards and the completion limit
each read off the tables above - admitted only while their quest rows are in the build. The collects and
deliveries wait for the quest-items import, the quests whose offer or completion line the later client never
shipped wait for a dialog decision, and the hideout boss waits with world 113; all are recorded on #4134.

## Rewards

`scripts/cap110_rewards.py` imports the items that monster reward rules name and native lacks: 94 alchemy materials and
2 SD tokens, as `itemdata_110001.txt`, with `cap110-rewards.txt` beside it. Group IDs are offset by 1,000,000. The server
reads them in `loot.InitCap110`, which refuses a rule naming a native monster or group. Rewards ride
`SRO_CAP110_MONSTERS`. A client-only build writes no rewards file; its absence keeps the native consumables, while a
file that is present must still parse and carry rules.

Gear odds come only from the level class tables, so tomb gear is rare by design. The website's drop lists describe the
native rule, not `SRO_PHARAOH_TOMB_GEAR_RATE`.

`SRO_ALCHEMY_MATERIAL_DROPS_OFF` discards every type 3/3/11/4 item, assigned drops included. While it is on, the 94
imported materials never drop; only the tokens do.

`SRO_ABOVE_DEGREE9_DROPS_OFF` (port-only, owner 2026-11-16) keeps every item above degree 9 out of monster drops while
the level cap stays 90 and the community polls decide what the new areas drop: equipment by its ItemClass, and the
alchemy goods of types 3/3/10 and 3/3/11 (elixirs, Lucky Powder, stones, tablets, elements), whose ItemClass is the
degree. Such a pick drops nothing and is not re-rolled, so every degree-9-and-below chance is unchanged; unique kills
are included, quest rewards are not drops and are unchanged. Off (the default) is native.

The SD tokens are in the gold-heap item group, whose body carries a u32 amount where other ETC groups carry a u16 stack
count. `ItemBody` handles this; `TestGoldGroupItemBodyCarriesU32Quantity` pins it.

## Blue Berserk quest items

`scripts/cap110_quest_items.py` imports the 18 quest items of the Alexandria Blue Berserk chains (`ITEM_QNO_SD_HW_*`:
fourteen ostracon items and four inscriptions, type 3/3/9/0) as `itemdata_110002.txt`, with their names merged into
`textdataname.txt`. Their model and icons are in the v1.150 tree, so nothing is copied from the later archives. The
items follow the item switch and the level cap, not the quests: they build when `SRO_CAP110_ITEMS` is on and
`SRO_LEVEL_CAP` is `110`, whether or not the quests exist. Identities are fresh and kept in
`.opensro-cap110-quest-items.json`; turning the switch off removes the shard, its manifest line and its names. The
quests themselves (and what exists only for them) are a separate switch, `SRO_CAP110_QUESTS`, which is not built yet.

## Blue Berserk scrolls, shop rows and texts

`scripts/cap110_blue_berserk.py` imports the nine items of the Blue Berserk system the v1.150 tables lack
(`ITEM_ETC_SECOND_HWAN_SCROLL_01..04`, the buff item `ITEM_ETC_SECOND_HWAN` of the 100% gauge charge, and the time parameter
items `ITEM_ETC_INCREASE_HWAN_TIME_01..04`) as `itemdata_110003.txt`. The four scrolls are sold in the potion stores
(`STORE_{CA,CH,EU,KT,WC}_POTION_TAB1`): the tool adds their package, scrap and price rows and one good per tab, in the next free
slot of the tab. It also copies the level table `hwanleveldata.txt` and fills the texts: the item names and tooltips, the Blue titles of
both races, the level refusal and the time line. v1.150 holds some of these symbols with a blank English column; a blank row is
replaced by the later client's row, a row that has English keeps it. They follow `SRO_CAP110_ITEMS` with `SRO_LEVEL_CAP=110`,
independent of the quest switch. Off, the importer removes the shard, the shop rows and the table, and restores the replaced text
lines, so the native tables return byte for byte. Animation records, icons and models are native already; `item_grouping.txt` is
not read by the port and is not imported. The scroll's rules (tier requirement, charge, cooldown) are the server step.

## Blue Berserk quest rows and texts

`scripts/cap110_quest_tables.py` imports the four Blue Berserk chains' tables from the later client: the 52 quests (the Army
and Military Tests of levels 95 and 100 for both races, and the Alexandria steps of levels 105 and 110; ids 346 to 666, none
used in v1.150) into `questdata.txt`, `questcontentsdata.txt` (the later table's four extra trailing columns are dropped) and
`gameguidedata.txt`, and their strings into the one `textquest.txt` the v1.150 client reads. The v1.150 text holds many of these
keys with a blank English column; a blank row is replaced by the later client's whole row, a row with English keeps it, and
absent keys are appended. Not imported: `refqusetreward.txt` (a server table the v1.150 client lacks; the rewards ride the
quests' own specs) and `worldmapguidedata.txt` (not read by the port). They follow `SRO_CAP110_QUESTS` with
`SRO_LEVEL_CAP=110`; off, the importer removes the rows and restores the replaced lines, so the native tables return byte for
byte (a table without a final newline keeps none).

## Blue Berserk quest monsters

## Blue Berserk trial arenas

The Army Test (Chinese) and Military Test (European) trials, quests 1_1 and 2_1, run in instances whose terrain only the
later client has: region 22966 (sector 182, 89) for the Chinese test and 22454 (182, 87) for the European one. Each is a single
isolated region with no neighbours, region code or zone name. `scripts/cap110_quest_arenas.py` names them as two extra seeds of
the Alexandria stage 1 import (`import_vsro_alexandria.py`), so the existing variant build copies their terrain, objects,
navmesh and ground textures and enables them in the availability bitmap. They follow `SRO_CAP110_QUESTS` with
`SRO_LEVEL_CAP=110`, and need the Alexandria variant (`SRO_ALEXANDRIA`). **Run stage 1 again after switching the quest
switch**, because the variant build reads stage 1's last output. The two ritual instances (quests 1_5 and 2_5) use native
regions and need nothing here. Nothing here places a player; the instances come with the quests.

Two server rules belong to the trial arenas. Their floor is a sealed object-nav deck by design (a walled room in an isolated region),
which the enter-world stranded-spawn rescue would otherwise treat as stranded and refuse (no mainland to drop the player onto), so
both trial regions are **exempt from that rescue** (`WaterValidator.ExemptStrandedRescue`, wired in `wiring_hwan.go` only when the
quest rows exist); the ritual regions are native and keep the ordinary rule. And a refused **return home** (after the pass, the fail
countdown or the ten minutes) is logged (`hwan arena:` and `relocation:` lines name the refusing stage) and retried every 3 s up to five
times before the arena closes, so a player is never left standing in a closed arena.

Port-only arena rules (none is native): a player who leaves an arena early by a return scroll, a reverse return or a teleport (the ordinary
relocation sends the arena no leave event) is noticed on the arena's next tick: an undecided fight fails with the quest's failed notice, the
arena closes at once and the quest stays active, so the player can enter again (`hwanUpdate`; a passed fight shows no failure). The return
anchor such an exit leaves behind is cleared by the next entry (`advanceHwanEntry`), which still refuses a player really inside an
instance. The ritual stands in an open region with no walls, so its player is **leashed** to the fight: a destination click or a direction walk
beyond 60 map units of the ghost's spot is refused or stopped at the edge (`movement.Runtime.WalkAllowed`), and Ghost Walk and the Wizard's
Teleport are cut back to the same edge (`clampPositionGoal`); the trials are walled rooms and are not leashed. The Exorcist's ritual (region
25253) puts the ghost exactly at map X 5781, Y 1217, the owner's chosen open spot (`hwanRitualPoints`); the other ritual and the trials keep the
ring and redraw a landing point inside a closed object (`QuestMonsterSpawn.AvoidClosedObjects`, `SetSpawnClosedObjectCheck`), as a monster
inside a tree cannot be hit.

A GM can check an arena with **`/HWANARENA <ch|eu>`** (below); `/warp 22966 1043 52 1087` and `/warp 22454 1195 91 653` send the
same warp by hand.

## Blue Berserk quests and system

With `SRO_CAP110_QUESTS` built into the data and `SRO_LEVEL_CAP=110`, four quest chains turn a Berserker blue. A quest spec
loads only when its quest row exists, so a shard built without the switch has none of this. The mechanics come from the
1.188-era game data; the shipped quest texts are the player-facing words.

| Chain | Level | Quests | Needs |
| --- | --- | --- | --- |
| Army Test 1 (Chinese) / Military Test 1 (European) | 95 | `QNO_{CH,EU}_HWAN_1_1` to `1_6` (plus the side steps `1_3_1`, `1_4_1`) | Ch'in Tomb stone ghosts for the bell (`SRO_QINSHI_TOMB=on`; the server warns when it is off) |
| Army Test 2 / Military Test 2 | 100 | `QNO_{CH,EU}_HWAN_2_1` to `2_6` | chain 1 done |
| Alexandria 105 | 105 | `QNO_SD_HW_001`, `_017` to `_018`, `_021` to `_022`, `_002` to `_008` | chain 2 done; `SRO_ALEXANDRIA`, `SRO_PHARAOH_TOMB` (the tomb 2 monsters) |
| Alexandria 110 | 110 | `QNO_SD_HW_009` to `_016`, `_019` to `_020`, `_023` to `_024` | chain 105 done; the tomb 3 monsters |

Each chain needs its character level and the whole earlier chain. The trials and the soul rituals run in **private** instances
(one player; `hwan_arena.go`): the trial is "kill the commander or survive ten minutes" (a commander and archers at level 95, a
commander and a healer at level 100), the ritual's ghost counts only when its killer is in Berserk at that moment. The other
steps use quest tools (the bell, the Mountain Essence on a Yeoha, the Radiant Crystal dig at Cleopatra's Gate, the Niya trap).
Chain 1 ends in Blue Berserk level 1, chain 2 in 2, the 105 chain in 3 and the 110 chain in 4; the level is derived from the
completed quests (no extra saved field). For testing, a GM can type **`/SETBERSERK <character> <level 0-6>`**: it sets that
character's Blue Berserk level (and so the absorption, the scroll requirements and the title), tells the character, and keeps the
level until the shard process restarts (a restart returns the quests' level). Port-only GM test tooling, like `/SETSPEED`; it does
not touch the quests. **`/SETGAUGE <character> <balls 0-5>`** sets that character's Berserk gauge to exactly that many balls (refused
while a Berserk is active and the count would rise, as natively) and tells the character.
**`/HWANARENA <ch|eu>`** warps the GM to where the Army Test (ch) or Military Test (eu) trial's player lands (the same warp `/warp` sends, so the server still checks the GM privilege and the terrain), to see that the new arena is reachable and walkable; it needs a shard built with `SRO_CAP110_QUESTS`.

What a level does: while Berserk, **10 + 5 x (level - 1) percent** of all incoming damage is absorbed; the speed doubling is the base
Berserk's. The Energy of Life scrolls (sold by the potion NPCs) need the Blue level their tier names, put the 20 minute buff and
the extra Berserk seconds (5, 8, 11, 14) on the bar without a cooldown, and a **second scroll is refused while those rows stand**
(port-only: the client keeps one extension value). Using the buff's charge fills the gauge, clears the rows and starts the shared
20 minute cooldown. The level reaches the browser through the port-only `0x3FCB` frame (**release protocol 19**) at world entry and
when it rises, with the title as a notice; the server also pushes every online player's level to the whole division every 2 s
(a fallen level once as 0), so other players' Berserk body is the blue 2nd Hwan record (`SYSTEM_CH_HWAN2MODE`, shipped although its
Service column is 0) and their name plate carries the title (bold gold, before the name). The item cooldown groups still running ride
the world entry (`itemCooldowns`), so the scroll icons keep their sweep after a teleport. A Blue Berserk draws the Berserk gauge in the blue twin art the v1.150 data ships
(`pmi_jahwan_02*`: circle sheet, face, glow, burn sprites, button states; same sizes as the plain ones, listed in
`cifRuntimeImageCatalog.mjs` because no v1.150 layout names them).

**Not ported, on purpose.** Cutscene scripts (`script/q_script`) are not ported, because interpreting them would add a substantial
amount of client-side code (a script runner, a scripted camera, client-only objects and decorative skill effects) for about 12
seconds of staging per ritual. The quests work without them. Skipped: `qno_{ch,eu}_hwan_{1,2}_5`, and for the record the Baekryoung
and Roc entrance scripts the port never staged.

**The Annihilation Trap is not implemented.** In the level 100 trial the original hands the player a trap (`ITEM_QNO_{CH,EU}_WHAN_2_1_01`,
skill `SKILL_QNO_{CH,EU}_WHAN_2_1_01_01`); when it closes on the trial's commander or healer, the quest puts that monster into AI state
0x1f ("not acting") for 10 seconds. The port cannot do that today, for two reasons. First, the trap skill's hook
(`CaptureQuestTrap`) is built around capture: it is told only the monster's codename and a closure that *defeats* it, so a quest cannot
reach the live monster to change its behaviour. Second, the monster owner has no "hold" a quest can call: its only timed stops are the
abnormal statuses (stun, freeze, sleep) that a *skill* applies through the skill and damage plumbing, and a hold that ignored the monster's
AI, resistances and the status board would be a new mechanic, not the original's. So the General hands out no trap and the trial is the
commander and the healer against the player; the trap item and skill stay in the data, unused. Adding it needs a monster-AI hold door in
`world/monster` first (a timed "not acting" state that the AI tick honours), then a quest hook that calls it for the trial's own monsters.

**Quest tools in the field** (`hwan_use.go`; the radii and odds are the port's reading of the 1.188-era game data, inferences marked in the
code). The **Soul-ringing Bell** works only within 100 world units (about 10 in-game metres) of the cemetery in region 23980 (x 1218, z 706;
`/warp 23980 1218 230 706`) and while the `QNO_{CH,EU}_HWAN_1_3_1` step runs; it summons the Old Tombstone Ghost and is spent either way. The
**Radiant Crystal** digs within 300 of Cleopatra's Gate (region 25954). With the Experimental row **Quest target markers** on (off by default),
the minimap and M also mark these two spots as quest markers (`quest-locations.ts`, port-only). The **Niya spirit trap** (and the level 100
trial's trap) draw their ground model: the later client marks the trap skills Service 0, so the asset build admits those three effect rows
(`parseSkillEffect.mjs`, as it does the second Hwan body), and a placement refused for a nearby trap or monster tells the player
(`CANNOT_MAKE_TRAP`, `CANNOT_MAKE_TRAP_EXIST_MONSTER`). The Niya quest pays gold for each Flutter Spirit held at the turn-in: the quest tables
carry no rate, so 10 each (capped at 10,000,000) is an inference. Traps can catch more Normal Spirits than the one the turn-in takes, and a
spare cannot be dropped or sold, so the turn-in takes every Normal Spirit held (`QuestSpec.QuestItemCleanup`; port-only, not native).

**Reverse return scroll destinations.** With `SRO_REVERSE_RETURN_MAP` on (the scroll's "move to a location on the map" choice) and the quest rows
built in, the map also offers **Exorcist's Home** (by Exorcist Miaoryeong's house near Jangan: map X 5775, Y 1225, region 25253) and
**Sunset Witch** (by the Sunset Witch near Constantinople: map X -10380, Y 3235, region 27728), the two ritual NPCs the chains send the player to
again and again. A third point, **Qin-Shi Tomb Entrance** (near where the game places a player leaving the tomb: map X 7200, Y 2080, region 26284),
joins whenever `SRO_QINSHI_TOMB` is on, with or without the quest rows: the 95 chain's bell comes from the tomb's stone ghosts, and shards at the
100 cap use the tomb too. They take the next public ids after the other points (`AddReverseReturnMapPoints`, `hwanReverseMapExtras` in
`wiring_hwan.go`). On the world map the Qin-Shi icon is drawn 40 px below its point so that it does not cover the map's own "open Ch'in
Tomb" button; its target does not move (`reverse-map-buttons.ts`).

**Verified in game by the owner (2026-11-09 and 10):** the blue gauge, the blue Berserk body and the bold gold title for the owner and for
other players; `/SETBERSERK` 0 to 6 and `/SETGAUGE`; the Energy of Life button, buff and cooldown for every tier (the extra Berserk seconds

Berserk" rule at the 95 chain's steps; and the three reverse return map points. **2026-11-17:** the first trial arena sends the player home
